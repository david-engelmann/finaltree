# finaltree contract

This contract is the executable spec for finaltree. Every obligation below maps to at least one named test in the test suite. An obligation is met only when its tests pass.

## The boundary

Finaltree asks what a gate ran on. Deadgate asks whether it ran, and blindgate asks what it read. Finaltree fingerprints the exact tree a gate ran on, binds that fingerprint to the evidence the gate reports, and verifies the fingerprint against a candidate tree before a verdict from the gate is trusted.

## Probe findings

The readings below rest on probes run against git on this machine with synthetic repos built for the check. The probes built a clean repo, a repo with staged but uncommitted changes, a repo with staged and unstaged and untracked changes standing together, a repo with a staged rename, a repo with a deleted tracked file, and a repo with an ignored build output folder.

Status in porcelain version 1 form with renames disabled reports a staged change in its first column and a worktree change in its second column, so one file can stand as both staged and modified at once and the two facts are separate entries in the reading. Untracked files carry question marks in both columns. A staged rename under the same flags reports as a deletion of the old path and an addition of the new path, and never as a paired record this slice must parse. A deleted tracked file reports as a worktree modification whose kind this reading names as modified.

The file list from ls-files names the paths in the index, and a staged addition stands in that list before any commit holds it, while the tree listing of HEAD names only what the last commit holds. A fingerprint of the tree a gate ran on therefore takes its tracked paths from the index and never from HEAD alone. Hash-object hashes the content of the file in the working tree. On the staged and modified probe file the hash-object result differed from the blob the index held, because the file had changed again after staging, and hash-object failed outright on the deleted file. The tracked blob in this reading is the hash of the working tree content, and a deleted tracked file carries no blob.

Status with untracked files shown still omits ignored files, and the ignored listing collapses an ignored folder into one folder entry. A generated artifact under an ignore rule is therefore invisible to every status reading, and the generated member of this reading is found by walking the files under the root and matching the declared patterns against them.

## Slice 2 obligations

- FT2-1 The fingerprint holds the HEAD commit of the tree. The commit is read with git rev-parse HEAD. A tree whose repo holds no commit is refused with a clear error and never fingerprinted with an empty commit member. Proven by test_fingerprint_holds_head_commit and test_repo_without_a_commit_is_refused.
- FT2-2 The fingerprint holds the tracked files as a list sorted by path. The paths come from the index, so a staged addition stands in the list before it is committed. Each entry carries the git blob hash of the working tree content of the file, and a tracked file deleted from the working tree carries a null blob in its entry. Proven by test_tracked_files_sorted_with_worktree_blob_hashes, test_staged_addition_is_tracked_before_commit, and test_deleted_tracked_file_carries_null_blob.
- FT2-3 The fingerprint holds the dirty files as entries of path and kind, sorted by path and then by kind. The kinds are staged and modified and untracked, read from status in porcelain version 1 form with renames disabled and untracked files shown. A file that is staged and then modified again carries both a staged entry and a modified entry. Proven by test_dirty_entries_name_each_kind and test_file_staged_and_modified_carries_both_entries.
- FT2-4 The fingerprint holds the generated artifacts as a list sorted by path. A generated artifact is a file under the root, outside the .git folder, whose relative path matches one of the declared generated patterns, whether git tracks it, ignores it, or has never seen it. Each entry carries the git blob hash of its content. An untracked file matching a declared pattern stands in the generated list and never in the dirty list as an ordinary untracked file. Patterns are matched with fnmatch rules where a double star crosses folders. Proven by test_generated_artifacts_match_declared_patterns, test_ignored_generated_artifact_is_listed, and test_generated_untracked_file_is_not_an_ordinary_dirty_entry.
- FT2-5 The fingerprint digest is the SHA-256 hex digest of one canonical serialization. The serialization is a JSON object holding the format name finaltree-fingerprint/1 and the commit and the tracked list and the dirty list and the generated list, with object keys sorted, with compact separators, and with every list in the sorted order its obligation states. The same members discovered in a different order give the same digest, and a change to any member changes the digest. The members themselves are retained beside the digest so a mismatch can be named and not just detected. Proven by test_digest_is_canonical_and_order_independent and test_any_member_change_changes_the_digest.
- FT2-6 Stamping binds a gate run to its fingerprint. The fingerprint is computed before the command runs, from the tree the command will run on. The command runs in the root without a shell, and its standard output and standard error are captured together in the order the command produced them. The stamped log carries a header a verifier can read back, holding the stamped log format name, the fingerprint digest, the full fingerprint as one JSON line, the generated patterns in force, the command, and the exit code. Every captured output line is written after a prefix holding the fingerprint digest, so every count line the gate reports is bound to the fingerprint. The stamped log is written even when the command exits nonzero, and the stamping command itself exits with the exit code of the gate command. Proven by test_stamp_binds_output_lines_to_the_fingerprint, test_stamp_writes_the_log_when_the_gate_fails, and test_stamp_returns_the_gate_exit_code.
- FT2-7 Verification answers match or mismatch and names every difference. The verifier reads the fingerprint from a stamped log header and computes the fingerprint of a candidate tree under the generated patterns the log records. The answer is match only when the commit and every tracked entry and every dirty entry and every generated entry agree. On a mismatch the verifier prints one line per differing member, naming a moved commit as a commit move, a changed tracked blob as a file content change, a tracked path standing on one side only as a tracked file added or removed, a dirty entry standing on the log side only as a dirty file cleaned, a dirty entry standing on the candidate side only as a dirty file added, and a generated entry that differs as a generated artifact difference. A generated artifact difference is never also reported as an ordinary file content change for the same path. The verify command exits zero on a match and one on a mismatch. Proven by test_verify_matches_the_tree_the_log_was_stamped_from, test_verify_names_a_moved_commit, test_verify_names_a_changed_file, test_verify_names_a_cleaned_and_an_added_dirty_file, and test_verify_names_a_generated_difference_as_generated.
- FT2-8 A stamped log that does not parse is refused. A log whose header lacks the fingerprint record, or whose fingerprint record does not decode, or whose recorded digest disagrees with the digest of its recorded members, or that carries an output line without the digest prefix, is refused with a clear error and the verify command exits two. Proven by test_verify_refuses_a_log_without_a_fingerprint_record and test_verify_refuses_a_log_whose_digest_disagrees_with_its_members.
- FT2-9 Fingerprinting and verification write nothing into the tree they read. Stamping writes only the stamped log at the path it is given. No operation in this slice uses the network. Proven by test_fingerprint_and_verify_leave_the_tree_unchanged.

## Rust port slice 1

The port ground is the landed Python of Round 1 with its review fixes. The Python package is the spec and the port reproduces its readings exactly on the surface this slice ports. The probes below were run against the Python runtime and against git on the building machine before the port was written.

The duplicate key probe read a fingerprint record whose JSON text carries the commit key twice and found the decoder keeping the last value standing, with the record accepted when the surviving value agrees with the recorded digest and refused on the digest when it does not. A second probe found the record reading taking the index blobs and the untracked list and the generated patterns from a record only when they stand in it, each reading as empty when it does not, and a record carrying a key the reading does not name standing accepted with that key left unread. A fifth probe found the JSON decoder accepting the NaN and Infinity spellings as numbers standing inside a record, with the record then standing or falling on its digest like any other record.
